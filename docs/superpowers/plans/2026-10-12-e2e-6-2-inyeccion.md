# E2E 6.2: inyección de eventos (duplicado, inválido y fuera de orden) — Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Agregar a `e2e/lib.sh` los ayudantes para inyectar eventos en RabbitMQ y leer el log del Catálogo, y los tres escenarios que los usan: 06 mensaje duplicado, 07 mensaje inválido a la DLQ y 09 eventos fuera de orden.

**Architecture:** Los eventos se publican a mano en el exchange `inventory.events` con la API de gestión de RabbitMQ (`POST /api/exchanges/%2F/inventory.events/publish`) y se comprueba su efecto con el log del Catálogo (las líneas `event_applied`, `event_duplicate` y `event_stale` llevan el `eventId`) y con los conteos de las colas (`rabbitmqctl`). Los escenarios 06 y 09 usan `CALCETINES-PACK-3` con versiones basadas en el reloj, de modo que se pueden repetir sin reset.

**Tech Stack:** bash, curl, jq, Docker Compose, API de gestión de RabbitMQ (usuario `retail`).

**Spec:** `docs/superpowers/specs/2026-10-12-e2e-design.md` (§2 `lib.sh`, §3 escenarios 06, 07 y 09, §6 Pendientes). Comportamiento del Catálogo: `docs/superpowers/specs/2026-10-12-catalogo-design.md` §6.

## Global Constraints

- Nombres de archivos, funciones y variables en **inglés y completos**; mensajes de salida, comentarios y documentación en **español**. Commits en inglés, Conventional Commits, con `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`.
- `set -uo pipefail` **sin `-e`**; todos los `.sh` ejecutables. Requieren bash 5 y GNU `date` (`%3N`).
- Se ejecutan contra el stack de desarrollo (proyecto Compose `retail`) con los puertos por defecto; consola de RabbitMQ `http://127.0.0.1:15672` (variables opcionales `RABBITMQ_MANAGEMENT_URL`, `RABBITMQ_MGMT_PORT`, `RABBITMQ_USER`, `RABBITMQ_PASSWORD`; por defecto `retail`/`retail-demo`).
- Exchange `inventory.events`, clave de enrutamiento `inventory.stock.changed`, cola `catalog.inventory-stock-changed`, DLQ `catalog.inventory-stock-changed.dlq`. Conteos de cola con `rabbitmqctl`, no con la consola.
- Versiones de los eventos inyectados: `V` = milisegundos desde la época (`version_base`); 06 usa `V` y `V+1`; 09 usa `V+2` y luego `V+1`. `CALCETINES-PACK-3` es el SKU de 06 y 09 (su estado en el Catálogo diverge del de Inventario por diseño, ver `docs/seed-data.md`, por eso no usan `require_synced`).
- Cada comprobación que depende de una consulta valida que el valor leído sea un entero (`is_integer`) antes de compararlo (lección de la 6.1: dos lecturas vacías serían "iguales").
- Los conteos de la DLQ se comparan con una línea base (`dlq_before`): la DLQ acumula mensajes entre ejecuciones.
- La ruta del repositorio contiene espacios: toda ruta en el código va entre comillas dobles.

## Review Focus

1. **Falsos positivos al repetir:** el stock inyectado (15, 12) puede coincidir con el de la ejecución anterior, así que esperar solo el stock pasaría sin que el mensaje se haya procesado. Los escenarios 06 y 09 esperan la línea del log con el `eventId` único. Se comprueba repitiendo cada uno y con las mutaciones de la Tarea 2.
2. **Mensaje que el broker no enruta** (clave equivocada o exchange inexistente): `publish_raw` devuelve 1 y cada escenario lo comprueba (`el broker enruta…`); sin eso el escenario fallaría por tiempo agotado en vez de por la causa. Se comprueba con la mutación de la clave.
3. **Mensajes venenosos:** los tres de 07 (JSON corrupto, sin `newStock`, SKU desconocido) deben quedar en la DLQ (línea base + 3), la cola principal en 0 y una venta real posterior debe llegar al Catálogo (la cola no se bloqueó).
4. **DLQ con residuos de ejecuciones anteriores:** se usa siempre la diferencia con `dlq_before`; se comprueba repitiendo 07 sin reset.
5. **Duplicado descartado por `eventId`, no por versión:** 06 reenvía el mismo `eventId` con una versión mayor y otro stock; el stock debe quedar como el primero y el log debe registrar dos `event_duplicate`.
6. **Cuerpos con comillas o saltos de línea en la publicación:** `management_publish_body` construye el JSON con `jq`, no con concatenación; lo fija la autoprueba.

```bash
# queue_messages_is <cola> <cantidad> (para wait_until)
queue_messages_is() { [[ "$(queue_messages "$1")" == "$2" ]]; }

# --- Inyección de eventos en RabbitMQ (por la API de gestión) y logs del Catálogo ---

# new_uuid: UUID aleatorio (Linux).
new_uuid() { cat /proc/sys/kernel/random/uuid; }

# version_base: base para las versiones de los eventos inyectados, a partir del reloj (milisegundos desde la
# época). Crece siempre, así que supera cualquier versión ya aplicada y el escenario se puede repetir sin reset.
version_base() { date +%s%3N; }

# build_event <eventId> <sku> <stock> <versión> [canal]: JSON de un evento InventoryStockChanged válido,
# con occurredAt = ahora (UTC, milisegundos).
build_event() {
  local occurred_at
  occurred_at="$(date -u +%Y-%m-%dT%H:%M:%S.%3NZ)"
  jq -cn --arg id "$1" --arg sku "$2" --argjson stock "$3" --argjson version "$4" \
    --arg channel "${5:-POS}" --arg at "$occurred_at" \
    '{eventId: $id, eventType: "InventoryStockChanged", sku: $sku, newStock: $stock,
      stockVersion: $version, channel: $channel, occurredAt: $at}'
}

# management_publish_body <cuerpo>: cuerpo de la petición de publicación de la API de gestión de RabbitMQ.
management_publish_body() {
  jq -cn --arg payload "$1" --arg key "$EVENT_ROUTING_KEY" \
    '{properties: {content_type: "application/json", delivery_mode: 2}, routing_key: $key,
      payload: $payload, payload_encoding: "string"}'
}

# publish_raw <cuerpo>: publica el cuerpo tal cual en el exchange de eventos. Devuelve 0 solo si el broker
# lo enruta a una cola (routed=true).
publish_raw() {
  local routed
  show "PUBLISH $EVENT_EXCHANGE / $EVENT_ROUTING_KEY  $1"
  routed="$(curl -s --max-time 10 -u "$RABBITMQ_USER:$RABBITMQ_PASSWORD" -H 'Content-Type: application/json' \
    -X POST "$RABBITMQ_MANAGEMENT_URL/api/exchanges/%2F/$EVENT_EXCHANGE/publish" \
    -d "$(management_publish_body "$1")" | jq -r '.routed')"
  [[ "$routed" == "true" ]]
}

# publish_event <sku> <stock> <versión> [eventId] [canal]: publica un evento válido. Deja su eventId en
# LAST_EVENT_ID (nuevo si no se indica). Devuelve 0 si el broker lo enruta.
publish_event() {
  LAST_EVENT_ID="${4:-$(new_uuid)}"
  publish_raw "$(build_event "$LAST_EVENT_ID" "$1" "$2" "$3" "${5:-POS}")"
}

# catalog_log_count <patrón>: líneas del log del Catálogo que contienen el patrón (texto literal).
catalog_log_count() { compose logs --no-color catalog-service 2>/dev/null | grep -c -F -- "$1"; }
# catalog_log_count_is <patrón> <cantidad> (para wait_until)
catalog_log_count_is() { [[ "$(catalog_log_count "$1")" == "$2" ]]; }
```

- [ ] **Step 1: Escenario 06 (mensaje duplicado)**

`e2e/06-duplicate-message.sh`:

```bash
#!/usr/bin/env bash
# Escenario 6 — Mensaje duplicado (spec global §4.2): el eventId ya registrado se reconoce y se confirma sin
# cambios. Inyecta eventos de CALCETINES-PACK-3 directamente en RabbitMQ (su estado en el Catálogo diverge del
# de Inventario por diseño, ver docs/seed-data.md). Uso: e2e/06-duplicate-message.sh [--demo]
set -uo pipefail
source "$(dirname "${BASH_SOURCE[0]}")/lib.sh"
e2e_init "$@"
SKU="CALCETINES-PACK-3"
STOCK=15

require_stack
dlq_before="$(queue_messages "$DEAD_LETTER_QUEUE")"
[[ "$(is_integer "$dlq_before")" == "yes" ]] || fail_precondition "no se pudo leer la cola $DEAD_LETTER_QUEUE"
base="$(version_base)"
event_id="$(new_uuid)"
applied_log="event_applied sku=$SKU eventId=$event_id"
duplicate_log="event_duplicate sku=$SKU eventId=$event_id"

step "Inyecta un evento nuevo de $SKU (stock $STOCK, versión $base)"
publish_event "$SKU" "$STOCK" "$base" "$event_id"
check "el broker enruta el evento a la cola" "$?" "0"
wait_until "el Catálogo aplica el evento (log event_applied)" catalog_log_count_is "$applied_log" 1
check "el Catálogo muestra stock $STOCK" "$(catalog_stock "$SKU")" "$STOCK"

step "Reenvía exactamente el mismo mensaje"
publish_event "$SKU" "$STOCK" "$base" "$event_id"
check "el broker enruta el duplicado a la cola" "$?" "0"
wait_until "el Catálogo reconoce el duplicado (log event_duplicate)" catalog_log_count_is "$duplicate_log" 1

step "Reenvía el mismo eventId con otra versión y otro stock: debe descartarse por eventId, no por versión"
publish_event "$SKU" 3 "$((base + 1))" "$event_id"
check "el broker enruta el mensaje a la cola" "$?" "0"
wait_until "el Catálogo vuelve a reconocer el duplicado" catalog_log_count_is "$duplicate_log" 2

step "Comprobando que no cambió nada"
check "el stock sigue siendo el del primer evento" "$(catalog_stock "$SKU")" "$STOCK"
check "el evento se aplicó una sola vez" "$(catalog_log_count "$applied_log")" "1"
wait_until "la cola $QUEUE queda vacía" queue_is_empty "$QUEUE"
check "la DLQ no recibió mensajes" "$(queue_messages "$DEAD_LETTER_QUEUE")" "$dlq_before"

finish "06 Mensaje duplicado"
```

```bash
#!/usr/bin/env bash
# Escenario 9 — Eventos fuera de orden (spec global §4.2): un evento con stockVersion menor o igual al guardado
# se ignora con ack; el estado final es el del más reciente. Inyecta la versión V+2 y luego la V+1 de

NEWER_STOCK=12
OLDER_STOCK=14

require_stack
dlq_before="$(queue_messages "$DEAD_LETTER_QUEUE")"
[[ "$(is_integer "$dlq_before")" == "yes" ]] || fail_precondition "no se pudo leer la cola $DEAD_LETTER_QUEUE"
base="$(version_base)"
newer_id="$(new_uuid)"
older_id="$(new_uuid)"

step "Inyecta primero el evento más reciente (versión V+2, stock $NEWER_STOCK)"
publish_event "$SKU" "$NEWER_STOCK" "$((base + 2))" "$newer_id"
check "el broker enruta el evento reciente" "$?" "0"
wait_until "el Catálogo aplica el evento reciente (log event_applied)" \
  catalog_log_count_is "event_applied sku=$SKU eventId=$newer_id" 1
check "el Catálogo muestra stock $NEWER_STOCK" "$(catalog_stock "$SKU")" "$NEWER_STOCK"

step "Inyecta después el evento anterior (versión V+1, stock $OLDER_STOCK), que llega tarde"
publish_event "$SKU" "$OLDER_STOCK" "$((base + 1))" "$older_id"
check "el broker enruta el evento tardío" "$?" "0"
wait_until "el Catálogo descarta el evento tardío (log event_stale)" \
  catalog_log_count_is "event_stale sku=$SKU eventId=$older_id" 1

step "Comprobando que el estado final es el del evento más reciente"
check "el stock sigue siendo el del evento más reciente" "$(catalog_stock "$SKU")" "$NEWER_STOCK"
check "el evento tardío no se aplicó" "$(catalog_log_count "event_applied sku=$SKU eventId=$older_id")" "0"
wait_until "la cola $QUEUE queda vacía" queue_is_empty "$QUEUE"
check "la DLQ no recibió mensajes" "$(queue_messages "$DEAD_LETTER_QUEUE")" "$dlq_before"

finish "09 Eventos fuera de orden"
```

`e2e/07-invalid-message.sh`:

```bash
#!/usr/bin/env bash
# Escenario 7 — Mensaje inválido (spec global §4.2): un mensaje que nunca podrá procesarse se rechaza sin
# reencolar, termina en la DLQ y no bloquea la cola. Inyecta JSON corrupto, un evento sin campo obligatorio y
# un evento de un SKU desconocido; después hace una venta real. Uso: e2e/07-invalid-message.sh [--demo]
set -uo pipefail
source "$(dirname "${BASH_SOURCE[0]}")/lib.sh"
e2e_init "$@"
SKU="TENIS-RUNNER-42"

require_stack
require_synced "$SKU"
require_stock "$SKU" 1
dlq_before="$(queue_messages "$DEAD_LETTER_QUEUE")"
[[ "$(is_integer "$dlq_before")" == "yes" ]] || fail_precondition "no se pudo leer la cola $DEAD_LETTER_QUEUE"
stock_before="$(catalog_stock "$SKU")"
base="$(version_base)"

step "Inyecta un mensaje con JSON corrupto"
publish_raw '{ esto no es json'
check "el broker enruta el mensaje corrupto" "$?" "0"

step "Inyecta un evento sin el campo obligatorio newStock"
publish_raw "$(build_event "$(new_uuid)" "$SKU" 1 "$base" | jq -c 'del(.newStock)')"
check "el broker enruta el evento incompleto" "$?" "0"

step "Inyecta un evento de un SKU que el Catálogo no conoce"
publish_event "SKU-INEXISTENTE-E2E" 3 "$base"
check "el broker enruta el evento de SKU desconocido" "$?" "0"

step "Esperando que los tres mensajes lleguen a la DLQ"
wait_until "la DLQ recibe los 3 mensajes" queue_messages_is "$DEAD_LETTER_QUEUE" "$((dlq_before + 3))"
wait_until "la cola $QUEUE queda vacía (nada reencolado)" queue_is_empty "$QUEUE"
check "el stock de $SKU en el Catálogo no cambió" "$(catalog_stock "$SKU")" "$stock_before"

step "Una venta real posterior debe llegar al Catálogo: la cola no se bloqueó"
sell "$SKU" POS
check "la venta responde 201" "$SELL_STATUS" "201"
wait_until "el Catálogo muestra stock $((stock_before - 1))" catalog_stock_is "$SKU" "$((stock_before - 1))"
check "la DLQ sigue con solo los 3 mensajes de este escenario" "$(queue_messages "$DEAD_LETTER_QUEUE")" "$((dlq_before + 3))"

finish "07 Mensaje inválido"
```
