# Fase 6 — Pruebas de integración de extremo a extremo (E2E) — Especificación de diseño

**Fecha:** 2026-10-12
**Fase:** 6 (integración y escenarios de fallo), una spec y un plan por sub-tarea (6.1 a 6.4)
**Contexto:** [spec global](2026-10-09-solucion-global-design.md) §4, §5 y §6 ·
[infraestructura](2026-10-10-infraestructura-design.md) · [Inventario](2026-10-11-inventario-design.md) ·

## 1. Objetivo y alcance

Demostrar, con los dos servicios y RabbitMQ corriendo juntos en Docker Compose, que **los 11 escenarios de
la spec global (§4.2) se comportan como se especificó**, y obtener la **medición de latencia reproducible**
(criterios de éxito 2 y 3). Es la evidencia que usan la fase 7 (pruebas de escritorio) y la fase 8
(documento y video).

Son scripts `bash` con `curl`, `jq` y Docker Compose. **No se escribe código Java nuevo**: las pruebas de
integración por servicio ya cubren la lógica; aquí se prueba el sistema completo con fallos reales
(contenedores detenidos y mensajes publicados a mano).

### Decisiones que fijan el diseño

- **Se ejecutan contra el stack de desarrollo, con los puertos por defecto** (Inventario 8081, Catálogo 8082,
  consola de RabbitMQ 15672): es el mismo stack que se ve en el video y en la consola de RabbitMQ. No usan un
  proyecto Compose aislado como los `smoke-*`. Los puertos se leen de las mismas variables que el Compose
  (`INVENTORY_SERVICE_PORT`, `CATALOG_SERVICE_PORT`, `RABBITMQ_MGMT_PORT`).
- **Los 11 escenarios son E2E**, también el 06 (duplicado) y el 09 (fuera de orden), que la tabla de cobertura
  de la spec global marcaba solo como integración: se inyectan eventos directamente en RabbitMQ con
  `CALCETINES-PACK-3` (ver `docs/seed-data.md`) y son parte de lo que se muestra en el cierre del video.
- **Fuera de alcance (YAGNI):** el escenario "base de datos del Catálogo caída" (decidido en la spec global),
  un simulador de carga, la reproducción del "antes" por lotes y el reprocesamiento de la DLQ.

## 2. Estructura y convenciones

```
e2e/
├── lib.sh                  # funciones comunes, sin lógica de escenarios
├── selftest.sh             # prueba de la lógica de lib.sh, sin Docker
├── reset.sh                # estado inicial conocido
├── sale-flow.sh            # flujo común de los escenarios 01 y 02 (se carga con source)
├── run-all.sh              # los 11 escenarios y el resumen
├── 01-pos-sale.sh   02-online-sale.sh   03-last-unit-race.sh   04-out-of-stock.sh
├── 05-catalog-down.sh   06-duplicate-message.sh   07-invalid-message.sh
├── 08-broker-down.sh   09-out-of-order.sh   10-security.sh
└── 11-latency.sh
```

- **Un escenario = un script autónomo**, ejecutable solo (`e2e/03-last-unit-race.sh`) o desde `run-all.sh`,
  con su propio SKU de `docs/seed-data.md`. Termina con código `0` si todas sus comprobaciones pasan.
- **Convenciones del repositorio:** nombres de archivos, funciones y variables en inglés y completos; mensajes
  de salida y comentarios en español. `set -uo pipefail` sin `-e` (se ejecutan todas las comprobaciones y se
  agrega el resultado, como en los `smoke-*`).
- **Variables de entorno** (todas opcionales): `INVENTORY_URL`, `CATALOG_URL`, `RABBITMQ_MANAGEMENT_URL`,
  `RABBITMQ_USER`/`RABBITMQ_PASSWORD` (`retail`/`retail-demo`), `WAIT_TIMEOUT_SECONDS` (30),
  `LATENCY_SALES` (20), `LATENCY_P95_LIMIT_MS` (1000) y `DEMO`. El tiempo máximo de espera también puede
  cambiarse por llamada anteponiendo la variable, por ejemplo `WAIT_TIMEOUT_SECONDS=90 wait_until "…" condición`
  (en bash la asignación vale solo durante esa llamada); está pensado para el escenario 08.
- **Tokens:** `scripts/generate-token.sh` (`pos`, `online`, `operator`, `no-scope`).

### `lib.sh`

| Función | Qué hace |
|---|---|
| `check <descripción> <obtenido> <esperado>` | Imprime `PASS`/`FAIL` y acumula el estado, igual que los `smoke-*` |
| `wait_until <descripción> <comando…>` | Reintenta cada 200 ms hasta `WAIT_TIMEOUT_SECONDS`; imprime `PASS`/`FAIL`, deja el tiempo esperado en `WAITED_MS` y devuelve 0 o 1 |
| `step <texto>` | Narra un paso (ver modo demo) |
| `e2e_init "$@"` | Procesa `--demo`; cualquier otro argumento imprime el uso y termina con `exit 2` |
| `is_integer <valor>` | Imprime `yes`/`no` según el valor sea un entero |
| `queue_is_empty <cola>` | Éxito si la cola no tiene mensajes (para `wait_until`) |
| `require_synced <sku>` | Espera a que el Catálogo coincida con Inventario para ese SKU |
| `sell <sku> <canal> [token] [cantidad]` | `POST` de una venta (sin token usa el del canal; con `""` no envía `Authorization`); deja el código HTTP en `SELL_STATUS` y el cuerpo en `SELL_BODY` |
| `catalog_product <sku>` / `catalog_field <sku> <filtro jq>` / `catalog_stock <sku>` / `catalog_stock_is <sku> <stock>` | Consultas del Catálogo (la última, éxito si coincide, para `wait_until`) |
| `inventory_stock <sku>` | Stock actual según Inventario (token de operador) |
| `http_status <url>` | Código HTTP de un `GET` sin autenticación |
| `token <pos\|online\|operator\|no-scope>` | JWT de demo con `scripts/generate-token.sh` |
| `fail_precondition <mensaje>` | Termina el escenario con `exit 1` y el aviso "estado no inicial: ejecuta `e2e/reset.sh`" |
| `outbox_count <sku>` / `outbox_count_is <sku> <n>` / `outbox_event_published <eventId>` | Eventos del SKU entre los 50 más recientes del outbox; comparación con un número (para `wait_until`); éxito si el evento figura `PUBLISHED` |
| `queue_messages <cola>` | Mensajes de una cola con `rabbitmqctl list_queues` (valor exacto, sin el retraso de las estadísticas de la consola) |
| `publish_raw <cuerpo>` | Publica el cuerpo tal cual en el exchange `inventory.events` (clave `inventory.stock.changed`) por la API de gestión; devuelve 0 solo si el broker responde `routed: true` |
| `publish_event <sku> <stock> <versión> [eventId] [canal]` | Construye un evento válido con `build_event` y lo publica; deja el `eventId` en `LAST_EVENT_ID` |
| `build_event <eventId> <sku> <stock> <versión> [canal]` | JSON de un `InventoryStockChanged` válido con `occurredAt` = ahora |
| `management_publish_body <cuerpo>` | Cuerpo de la petición de publicación (construido con `jq`, conserva comillas y saltos de línea) |
| `new_uuid` / `version_base` | UUID aleatorio / milisegundos desde la época (base de las versiones inyectadas) |
| `catalog_log_count <patrón>` / `catalog_log_count_is <patrón> <n>` | Líneas del log del Catálogo con ese texto literal (para `wait_until`) |
| `queue_messages_is <cola> <n>` | Éxito si la cola tiene exactamente `n` mensajes (para `wait_until`) |
| `require_stack` / `require_stock <sku> <mínimo>` | Precondiciones: herramientas, servicios sanos y stock suficiente; si no, falla con "estado no inicial: ejecuta `e2e/reset.sh`" |
| `stop_service <servicio>` / `start_service <servicio>` | Registra el contenedor (una sola vez) y lo detiene; si `compose stop` falla, devuelve 1 pero lo deja registrado / lo levanta (`up -d --wait --no-recreate`, idempotente), espera a que esté sano y lo quita del registro; devuelven 1 si `compose` falla |
| `install_restore_trap` / `restore_services` | Trap de salida (EXIT; INT → 130, TERM → 143) que levanta lo que el escenario dejó detenido; ignora INT y TERM mientras restaura y avisa por el stderr original, aunque la señal llegue dentro de un `wait_until` |
| `now_ms` / `metric <nombre> <valor>` | Milisegundos desde la época / imprime `METRIC <nombre>=<valor>` (formato que recoge `run-all.sh`) |
| `queue_consumers <cola>` / `queue_consumers_is <cola> <n>` | Consumidores de una cola (`rabbitmqctl`) |
| `outbox_count_with_status <estado> <eventId…>` / `outbox_count_with_status_is <estado> <n> <eventId…>` | Cuántos de esos eventos tienen ese estado en el outbox |
| `catalog_applied_sequence <sku> <eventId…>` | Los `eventId` pedidos que el Catálogo aplicó, en el orden del log (devuelve 1 si no puede leerlo) |
| `statistics <valores…>` | Deja `STAT_MIN`, `STAT_AVERAGE`, `STAT_P95` y `STAT_MAX`; devuelve 1 sin valores |
| `finish <nombre>` | Imprime el resultado del escenario y termina con `exit` con el estado acumulado |

Requiere bash 5 y GNU `date` (`date +%s%N`); no funciona con bash 3.2 ni con el `date` de macOS.

La API de gestión se usa para **publicar** (`POST /api/exchanges/%2F/inventory.events/publish`); los conteos
de colas salen de `rabbitmqctl` porque la consola actualiza sus estadísticas con retraso. Se confirmó en 6.2
que el exchange enruta lo publicado así (`{"routed": true}`) y que una clave desconocida responde
`{"routed": false}`; los escenarios comprueban el valor devuelto por `publish_raw`.

### Modo demo

`--demo` o `DEMO=1` en un script suelto: `step` narra en español cada paso, muestra la petición y la
respuesta resumida, y espera Enter. Sin demo, `step` imprime una sola línea. `run-all.sh` no admite demo.

## 3. Escenarios

Todos leen el estado inicial de la API (no suponen la semilla), actúan y esperan con `wait_until`, nunca con
pausas fijas.

| # | SKU | Acción | Comprobaciones |
|---|---|---|---|
| 01 POS, 02 online | `TENIS-RUNNER-42` | Venta de 1 unidad con token `pos` / `online` | `201` con el stock restante; el Catálogo converge a `antes − 1`; `lastEventLatencyMs` es numérico; el evento figura `PUBLISHED` en el outbox |
| 03 Carrera | `BALON-FUTBOL-5` (stock 1) | Dos ventas simultáneas (POS y online, en segundo plano) | Un `201` y un `409`; stock 0 en Inventario; **un solo evento** nuevo para el SKU en el outbox; el Catálogo converge a 0 (`inStock=false`) |
| 04 Sin stock | `CAMISETA-DRYFIT-M` (stock 0) | Una venta | `409` en `problem+json`; stock sin cambios; **cero eventos nuevos** en el outbox |
| 05 Catálogo caído | `MOCHILA-TRAIL-20L` | `docker compose stop catalog-service`, 3 ventas, `start` | La cola acumula 3 mensajes; tras reiniciar, el Catálogo converge a `antes − 3`, los eventos se aplican **en el orden de las ventas** (verificado con el log del Catálogo) y la cola queda vacía. **Mide** el tiempo de puesta al día (`catalog_catch_up_ms`). Consume 3 unidades de MOCHILA: caben 3 ejecuciones por reinicio |
| 06 Duplicado | `CALCETINES-PACK-3` | Inyecta el mismo evento dos veces y luego el mismo `eventId` con otra versión y otro stock | El stock queda con el primer valor (descartado por `eventId`, no por versión); el log del Catálogo muestra `event_duplicate`; la DLQ no crece |
| 07 Mensaje inválido | `TENIS-RUNNER-42` | Inyecta JSON corrupto, un evento sin campo obligatorio y uno con SKU desconocido; luego hace una venta real | La DLQ crece en 3 y la cola principal queda en 0; la venta posterior llega al Catálogo (**la cola no se bloqueó**) |
| 08 RabbitMQ caído | `BOTELLA-TERMICA-750` | `docker compose stop rabbitmq`, 2 ventas, `start` | Ambas dan `201`; el outbox las muestra `PENDING` y el Catálogo no cambia; al volver el broker pasan a `PUBLISHED` y el Catálogo converge a `antes − 2` (**cero eventos perdidos**), aplicados **en el orden de las ventas** (verificado con el log del Catálogo). **Mide** el tiempo de vaciado del outbox y de puesta al día del Catálogo (`outbox_drain_ms` y `broker_recovery_catch_up_ms`). Consume 2 unidades de BOTELLA: caben 5 ejecuciones por reinicio |
| 09 Fuera de orden | `CALCETINES-PACK-3` | Inyecta la versión `V+2` y luego la `V+1` | El stock final es el de `V+2`; el log muestra `event_stale`; la DLQ no crece |
| 10 Seguridad | `TENIS-RUNNER-42` | Venta sin token, con token basura, con token sin permiso (`no-scope`) y con token de operador | `401`, `401`, `403`, `403`; el stock no cambia; la consulta del Catálogo sin token da `200` |
| 11 Latencia | `GORRA-SPORT-NEGRA` | `LATENCY_SALES` ventas (20) alternando POS y online, una tras otra | Lee `lastEventLatencyMs` de cada una; calcula mínimo, promedio, p95 y máximo; escribe `docs/results/latency.md`; **falla si el p95 supera `LATENCY_P95_LIMIT_MS`** |

- **Versiones de los eventos inyectados (06 y 09):** `V` sale del reloj (milisegundos desde la época). Crece
  siempre, así que supera a cualquier versión ya aplicada y los escenarios se pueden repetir sin reset. El
  estado de `CALCETINES-PACK-3` en el Catálogo diverge del de Inventario por diseño (ver `docs/seed-data.md`).
- **Esperas de los escenarios de inyección (06, 09):** el stock inyectado puede coincidir con el de una
  ejecución anterior, así que no basta con esperar el stock: los escenarios esperan la línea del log del
  Catálogo (`event_applied`, `event_duplicate` o `event_stale`) con el `eventId` único del mensaje inyectado.
- **SKU compartido:** 01, 02, 07 y 10 usan `TENIS-RUNNER-42`, pero cada uno lee el stock actual y compara contra
  él (nunca contra la semilla), así que no se interfieren y se pueden correr en cualquier orden. El evento con
  SKU desconocido del 07 usa `SKU-INEXISTENTE-E2E`.
- **Precondiciones de stock:** los escenarios que consumen stock (01, 02, 03, 05, 07, 08, 11) comprueban antes que hay
  suficiente (`require_stock`); 03 exige además que el stock sea exactamente 1 (comprobación propia), así que
  solo corre una vez por reset. 01, 02 y 07 consumen una unidad de TENIS-RUNNER-42 cada uno (stock sembrado 5,
  compartido con 10): tras unas 5 ventas hace falta `e2e/reset.sh`. Se repiten sin límite 04, 06, 09 y 10.
- **Restauración:** 05 y 08 devuelven el sistema a su estado normal aunque fallen: un `trap` vuelve a levantar
  el contenedor detenido y espera a que esté sano. El `trap` cubre la salida normal (EXIT), Ctrl+C (código
  130) y SIGTERM (código 143); se comprobó con señales reales enviadas con el contenedor ya detenido, y el
  contenedor volvió `running/healthy`. Tras volver RabbitMQ, el Catálogo se reconecta solo
  (se observó en unos 25 s), por lo que el tiempo máximo de espera del 08 es mayor (90 s).
- **Tiempos medidos:** tras `docker compose start rabbitmq` el broker vuelve sano y el outbox y el Catálogo
  convergen en ≈ 5,9 s desde el reinicio (`outbox_drain_ms` 5843–5866; `broker_recovery_catch_up_ms`
  5856–5879). El Catálogo tarda ≈ 6,4 s en ponerse al día tras reiniciarlo en el 05 (`catalog_catch_up_ms`
  6409–6498, incluido el arranque del servicio). En la sub-tarea 5.4 se observó una vez una reconexión de hasta
  ~25 s; el tiempo máximo de espera de recuperación es 90 s. Las métricas solo se emiten si la espera pasó.
- **Informe de latencia (`docs/results/latency.md`):** fecha, `N`, los valores mínimo, promedio, p95 y máximo, y
  la comparación con el "antes" de la spec global §6 (peor caso 30 min, promedio ~15 min). La latencia es
  `lastEventLatencyMs` del Catálogo (`updatedAt − occurredAt`); los contenedores comparten el reloj del
  anfitrión. Se versiona en git como evidencia para el documento.
- **Seguridad del Catálogo (10):** sus consultas son públicas por diseño; el escenario solo afirma el `200` sin token.

## 4. Orquestación

- **`reset.sh`:** `docker compose down -v` y `docker compose up -d --wait --build`; espera a que ambos
  servicios estén sanos. Es destructivo para el stack de desarrollo, por eso **`run-all.sh` no lo invoca por
  defecto**.
- **`run-all.sh [--reset] [--report <archivo>]`:** verifica herramientas (`docker`, `curl`, `jq`) y que
  Inventario y Catálogo respondan (si no, indica `docker compose up -d --wait`); con `--reset` ejecuta antes
  `reset.sh`; corre los 11 escenarios en orden, cada uno en un subproceso aislado y **continúa tras un fallo**;
  imprime una tabla (escenario, PASS/FAIL, duración) y termina con código distinto de cero si alguno falló.
  `--report` escribe esa tabla en Markdown con las dos métricas secundarias (puesta al día del 05 y vaciado
  del 08); es opcional para no ensuciar el repositorio en cada ejecución.
- **Prueba de la propia herramienta:** `e2e/selftest.sh` (sin Docker) cubre la lógica de `lib.sh` con riesgo
  real: `statistics`, `wait_until` (éxito y tiempo agotado) y el estado acumulado de `check`. Los escenarios se
  prueban ejecutándolos contra Compose y comprobando que **fallan** al romper a propósito la condición
  (mutación manual, sin commitear). Se ejecuta `shellcheck` si está instalado.

## 7. Decisiones descartadas

| Alternativa | Motivo |
|---|---|
| Proyecto Compose aislado por ejecución (como los `smoke-*`) | No sirve para grabar el video ni para ver la consola de RabbitMQ en vivo; el stack de desarrollo es el que se muestra |
| Un modo aislado y otro de demo | Duplica la lógica de arranque y los casos sin aportar a ningún escenario |
| Pruebas E2E en Java (Testcontainers Compose, RestAssured) | Repite lo que ya cubren las pruebas de integración y contradice la spec global (bash) |
| Un único script con todos los escenarios | No se puede ejecutar un escenario suelto para grabarlo |
| `run-all.sh` que reinicia siempre el stack | Borraría datos de desarrollo sin avisar; el reinicio es explícito (`--reset`) |
| Pausas fijas (`sleep`) para esperar la convergencia | Lentas y frágiles; se espera la condición con tiempo máximo |
| Leer conteos de colas con la API de gestión | Sus estadísticas se actualizan con retraso; `rabbitmqctl` da el valor exacto |
| Informe de ejecución siempre escrito en el repositorio | Genera cambios en cada corrida; se genera solo con `--report` |
